The problem: a storage node is a whole stack

  • Serving block storage means owning everything: drive drivers, RAID, thin provisioning, snapshots, wire protocols, management, clustering.
  • The incumbents — SPDK, LIO, Ceph, ZFS — are decades of C/C++, kernel-entangled, and heavy to embed, package, or audit.
  • We wanted one engine that runs the same from a 200GbE flash node to a router with a USB disk — and that other Storm services can link, script, and boot from.

Single-node first, scale-out later.
A lone node must be fully useful; clustering is strictly optional.

The vocabulary, in plain terms

TermWhat it means here
Target / initiatorThe server side and client side of network block storage. StormBlock is the target; anything that mounts a disk over the network is an initiator.
iSCSI / NVMe-oFThe two wire protocols for "a disk over TCP". iSCSI (port 3260) is the 20-year veteran everything speaks; NVMe-oF (port 4420) is the fast modern one. StormBlock serves both.
LUN / namespaceOne exported disk, as the initiator sees it. A single target can serve thousands.
Thin provisioningA "100 GB" volume that only occupies the space actually written — and gives space back when files are deleted (discard/UNMAP).
COW snapshot / cloneCopy-on-write: a snapshot or clone copies no data, it shares the original's extents and diverges only where written. Instant, whatever the size.
Slab & extentEvery drive is formatted as a flat array of 1 MB slots — a slab. Volumes are stitched together from slots on any slab, any drive, any tier.
ublkA Linux 6.0+ interface that lets a userspace program appear as a local disk (/dev/ublkb0) — how a machine boots from StormBlock.
CSI / PVCKubernetes/OpenShift's storage plug interface. A pod asks for a PersistentVolumeClaim; the CSI driver turns that into a StormBlock volume.

The idea: organic storage, not carved pools

  • No rigid pools, no pre-sized virtual drives. Every device is a Slab — a flat array of 1 MB slots with an on-disk slot table and CRC32C metadata.
  • The Global Extent Map (GEM) is the single source of truth: volume extent → (slab, slot), with a reverse index — and it can be rebuilt from the slabs on recovery.
  • Volumes start at one slot and grow, shrink, and spread across devices and tiers as they're written and discarded. Placement moves extents later, live.

Snapshots clone the map, not the data. Discards free slots back to every volume on the device.

In plain terms: instead of slicing each disk into fixed partitions up front, every disk becomes a tray of 1 MB cells. Volumes are recipes — lists of which cells hold their data — and moving, copying, or snapshotting a volume is editing the recipe, not shoveling the bytes.

Drive layer: four backends, one trait

  • NVMe via VFIO — a full userspace NVMe driver: BAR0 mapping, hugepage DMA, per-core submission/completion queue pairs, MMIO doorbells. The kernel only hands over the PCIe device.
  • SAS via io_uring — O_DIRECT with registered buffers on kernel HBA drivers; SSD/HDD detection and serials from sysfs; SMART health on a REST endpoint.
  • iSCSI initiator — StormBlock can consume any iSCSI target as a drive: login, READ/WRITE(10), UNMAP, NOP keepalive. Remote disks become slabs.
  • FileDevice — plain files via tokio: MikroTik, dev machines, CI.
// every backend implements
trait BlockDevice {
  async fn read(&self, lba, buf);
  async fn write(&self, lba, buf);
  async fn flush(&self);
  async fn discard(&self, lba, len);
}
  • ublk server — volumes surface as local /dev/ublkbN via io_uring URING_CMD (Linux 6.0+): the root-disk path.
  • Shared-ring IPC — io_uring-style zero-copy rings over Unix socket + memfd + eventfd, for StormFS running on the same host.
In plain terms: everything above this layer sees "a disk" — whether the bytes live on a passed-through NVMe card, a SAS shelf, another machine's iSCSI export, or an ordinary file.

Slabs, the GEM, and honest thin provisioning

Volume Z (100 GB virtual)
 ├ extent 0 → Slab A (NVMe, Hot)  slot 42
 ├ extent 1 → Slab A (NVMe, Hot)  slot 43
 ├ extent 2 → Slab B (SAS, Warm)  slot 7
 └ extent 3 → Slab A (NVMe, Hot)  slot 100
  • Slab on-disk format: header, slot table (CRC32C), free bitmap. Slot-table updates are read-modify-write of one aligned sector.
  • Registry indexes slabs by tier (Hot/Warm/Cool/Cold) with best-fit allocation.
  • GEM keeps forward + reverse maps; snapshot = clone map + bump refcounts.

Reclaim, end to end

  • Targets advertise thin provisioning (SCSI VPD 0xB2, NVMe DSM) — so initiators actually send UNMAP/TRIM.
  • Discards flow through GEM and free slab slots back to the shared pool; /metrics exposes allocated vs free gauges.
  • WRITE SAME(10/16) with UNMAP, granularity/alignment advertised from the device (VPD 0xB0).
In plain terms: delete a file inside a VM, and the space comes back to the pool for every other volume — the full loop, from the guest filesystem down to the physical drive, actually closes.

Source

RAID engine: 1 / 5 / 6 / 10, SIMD parity

  • XOR parity and RAID 6's GF(2⁸) Q-syndrome in hand-written SIMD: AVX2 on x86_64, NEON on ARM, scalar fallback everywhere else.
  • Write-intent journal: dirty stripes marked before writes, cleared after — crash recovery re-syncs only what was in flight.
  • Background rebuild with rate limiting (foreground I/O keeps priority) and periodic scrub (read + parity verify).
  • RAID 1 supports dynamic add/remove member — not a maintenance feature, a migration primitive.

Add/remove member = live migration

RAID 1 on remote iSCSI diskmachine running from it
add_member(local NVMe) → rebuildmirror fills in the background
remove_member(remote)machine now runs on local disk — never rebooted
In plain terms: mirroring is also how data walks between machines: attach a new disk to the mirror, let it catch up, drop the old one. The volume never stops serving.

Two wire protocols, built for thousands of disks

iSCSI (:3260)

  • RFC 7143: full login negotiation, CHAP (constant-time MD5), header/data digests, multi-connection sessions, R2T/Data-Out.
  • MPIO/ALUA multipath; discovery sessions that real open-iscsi accepts.
  • Thin volumes export directly as LUNs — added and removed at runtime, O(1) lookup, tested at 1,000 attached LUNs and REPORT LUNS at 2,000.

NVMe-oF/TCP (:4420)

  • Discovery subsystem, fabric connect, full admin + I/O command sets, io_uring zero-copy send for read data.
  • Namespace hot-add: a host connects once; later volume attaches arrive as an async event + rescan — no new TCP session per container.
  • Per-core reactor pool with CPU pinning; LUN/NSID mappings persist across restarts (luns.json).
In plain terms: the design load isn't one big disk — it's a container platform where every instance gets its own cloned disk. Thousands of small disks, appearing and vanishing constantly, on one TCP connection per host.

The core workflow: golden image → clone per consumer

# create a volume, idempotent by name
curl -X POST node:9090/v1/volumes \
  -d '{"name":"fedora-golden",
       "size_bytes":10737418240}'

# clone it — copies no data (CoW)
curl -X POST node:9090/v1/volumes \
  -d '{"name":"instance-42",
       "source":{"volume":"fedora-golden"}}'

# export: returns LUN / NSID, goes active
curl -X POST node:9090/api/v1/exports \
  -d '{"volume_id":"…","protocol":"iscsi"}'
  • Untar a golden OS image once; every container/VM instance gets a CoW clone that shares the source's extents and diverges only where it writes.
  • Clone-and-attach measured at 1.46 ms p50 — fast enough that "give this sandbox a disk" sits on a request path.
  • Drop the instance → delete the clone → discards reclaim its diverged extents. Restart-to-reset for free.
  • Snapshots (/v1/snapshots) freeze any volume the same way; group snapshots freeze many under one consistency point.
In plain terms: like container images, but for disks: one master copy, unlimited cheap instances, each instance paying only for what it changes.

Features & usage

Machines boot from StormBlock

boot-iscsi — diskless first boot

  • Provisions a partitioned boot disk (esp:256M,boot:512M,root:6G,swap:1G,home:rest) as thin volumes on a remote iSCSI slab.
  • A minimal initramfs (busybox + stormblock + ublk_drv) logs in and exports each partition as /dev/ublkbN; Fedora installs and boots LinuxBoot-style — verified end-to-end in CI.

boot-local — every boot after

  • Attaches existing slabs non-destructively, restores metadata, resolves the boot volume by UUID/name, exports root as /dev/ublkb0.

Zeroboot flow-over

Machine boots from network slabroot on iSCSI, via ublk
--local-disk: migrate in backgroundper-extent lock cycling — root I/O keeps flowing
Next boot: fully localno reinstall, no downtime
In plain terms: rack a machine with a blank disk, power it on, and it boots an OS it doesn't have — then quietly copies that OS onto its own disk while running from it. StormBlock is serving the very volume it's migrating.

Features & usage

Cluster: optional, discoverable, replicated

  • Discovery — UDP multicast announcements with multi-cluster identity; the Nodes UI page shows discovered peers and drives cluster create/join/leave.
  • Metadata consensus — openraft 0.9 over HTTP/HTTPS, sharing the management TLS cert; heartbeat health monitoring marks unreachable peers.
  • Replication — synchronous (ack after N replicas) or asynchronous with a retry queue: exponential backoff, bounded at 10k entries, Prometheus counters for success/exhausted/dropped.

Placement engine

  • migrate_extent — move one extent live between slabs.
  • evacuate_slab — drain a device for removal.
  • rebalance — EvenDistribution or TierAffinity strategies across the pool; placement decisions consult discovered peers.
  • Snapshot-fenced cold copies for tiering data down without racing live writes.
In plain terms: nodes find each other by shouting on the LAN, agree on metadata by vote, and shuffle 1 MB cells between machines in the background — all of it optional; a single node never needs any of it.

The OpenShift interface: stormblock-csi

  • A sister repo makes StormBlock the platform's default StorageClass: CSI controller + node plugin + operator, all Rust (tonic gRPC, kube-rs).
  • Every PVC becomes a wandering replicated pair: a master replica local to the pod's node, a slave prestaged on a second worker.
  • CSI parity list: dynamic provisioning, online expansion, raw block, VolumeSnapshot + VolumeGroupSnapshot, clones via PVC dataSource, CSIStorageCapacity, WaitForFirstConsumer topology.

The /v1 contract: fencing as an API

Endpoint groupSemantics
/v1/volumes · snapshots · groupsName-idempotent create (CSI retries safely), CoW clone via source, expand, mode-gated attach/detach. Group snapshots hold GEM + registry locks across all members — one consistency fence.
…/placement · …/prestageConverge the master/slave pair; replace a slave with throttled background resync. Master==slave is a 409 — anti-affinity is mandatory, not advisory.
…/fence · …/promoteCompare-and-swap on a per-volume epoch: 412 stale_epoch tells a lagging controller it lost the race. A fenced old master can never ack a write again.
…/dual-attach (+ close)Bounded two-node window (TTL) for KubeVirt live migration; commit = fence + promote the target, sub-second cutover; abort = master unchanged.
/v1/nodes/capacityPer-node bytes + topology labels → CSIStorageCapacity and WaitForFirstConsumer scheduling.

The contract doc's MockEngine is the executable spec; StormBlock's implementation is verified by 11 HTTP-level integration tests ported straight from it. Errors are a typed envelope: {code, message, current_epoch?} over 404/409/412/507.

In plain terms: split brain — two nodes both believing they own a disk — is the storage disaster. Here it's prevented by arithmetic: every ownership change increments a counter, and writes carrying yesterday's number are refused.

Control-plane latency: measured, then halved

OperationBeforeAfter
Clone1.65 ms0.80 ms
Attach1.48 ms0.67 ms
Delete1.52 ms0.68 ms
Clone-and-attach p503.14 ms1.46 ms

GEM + slab registry moved from Mutex to RwLock; state saves diff-and-append instead of rewriting.

  • Flat, not linear. Clone latency vs existing volumes: 0.64 / 0.62 / 0.69 ms at ~21 / ~42 / ~63 volumes — previously 0.81 / 1.09 / 1.51 and climbing.
  • The old state save rewrote all control-plane JSON per mutation — extrapolating to ~85 ms per clone at 5,000 volumes, exactly the scale the registry model targets. Now: append the changed records, full snapshot every 512.
  • NVMe-oF hot-add means attach cost is an async event + rescan — no Connect, no new TCP session per new volume.
In plain terms: the fixes weren't "make it fast" — they were "stop it getting slower as it fills up." Cost per disk is now the same for the 10th and the 5,000th.

Lessons learned

The spec is the map; the initiator is the territory

SymptomRoot cause — always in the protocol fine print
Thin volumes grew forever, never shrankTwo independent causes: without VPD page 0xB2 Linux never issues discards at all; and UNMAP's parameter list arrives as a separate data-out phase that was never read. Either alone kept reclaim at zero.
iSCSI discovery "never worked"The target echoed SessionType back in the login response; open-iscsi aborts on the unexpected key. RouterOS masked the bug for months by skipping discovery entirely.
Session hangs after ~128 commandsExpStatSN wasn't tracked from response PDUs — the target's command window silently closed. Nothing errors; everything just stops.
Hosts never noticed new namespacesNVMe-oF hot-add needs the whole chain: OAES bit advertised, host's async event request held, Changed Namespace List log page (cleared on read, with the rescan-everything sentinel). Miss one link and no event ever fires.

Every one of these was found against a real initiator — open-iscsi, RouterOS, the Linux nvme host — not against the spec PDF. Interop testing is the test suite.

What's next

Open issues, sized honestly

Data path

  • Slab I/O to O_DIRECT + io_uring — today's buffered tokio file I/O is the known throughput ceiling (#30).
  • iSCSI MC/S or clean multi-session parallelism (#31).
  • Engine data path for cross-node replication: epoch-carrying writes and resync — the /v1 control plane is done, the bytes don't move yet.

Volume lifecycle

  • Online resize — ublk must learn the new size; shrink must refuse to eat a mounted filesystem (#19).
  • First-class volume move / re-home (#20).
  • Grow the pool on disk pressure: add a slab at 80% used instead of preallocating (#18).
  • CSI end-to-end on the 4-node cluster (stormblock-csi#15).

The pattern so far holds: control plane first with an executable spec, then make the data path honest against real initiators.
